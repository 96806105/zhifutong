# 04 · 错误处理与质量保障机制

> 面向工程实践的错误处理设计：统一错误规范、中间件防线、SQLite 事务安全、
> 以及「宁可兜底也不编造」的 LLM 幻觉防护。

---

## 1. 错误处理分层

智服通的错误处理遵循 **四层防线**，从请求入口到数据落地逐层兜底：

```
┌─────────────────────────────────────────────────────┐
│ Layer 1  中间件          鉴权失败 / 限流拒绝          │
│ Layer 2  API 路由         参数校验（Pydantic）        │
│ Layer 3  业务层          转人工决策 / 未命中兜底      │
│ Layer 4  全局异常处理      未捕获异常 → 统一 JSON     │
└─────────────────────────────────────────────────────┘
```

### 统一错误格式

所有接口错误均返回一致结构，便于前端统一处理与埋点：

```json
{
  "error": {
    "code": "SUPPORT_UNKNOWN",
    "message": "服务器开小差了，请稍后再试"
  },
  "detail": "..."
}
```

| 错误码 | 触发场景 | HTTP |
|---|---|---|
| `SUPPORT_AUTH_FAIL` | 管理接口未带/错误 `X-Admin-Token` | 401 |
| `SUPPORT_RATE_LIMIT` | 单 IP 短时写请求过多（令牌桶） | 429 |
| `SUPPORT_BAD_PARAM` | Pydantic 请求参数校验失败 | 422 |
| `SUPPORT_NOT_FOUND` | 会话/资源不存在 | 404 |
| `SUPPORT_CONFLICT` | 业务状态冲突 | 409 |
| `SUPPORT_INTERNAL` | 数据库/外部依赖异常 | 500 |
| `SUPPORT_UNKNOWN` | 未捕获的兜底异常 | 500 |

### 关键实现

`middleware/auth.py`

- **TokenAuthMiddleware**：`/api/admin`、`/api/kb` 白名单鉴权，`APP_SECRET` 为空时默认放行（便于演示）。
- **RateLimitMiddleware**：滑动窗口令牌桶，默认 30 次/60s/IP，只对写操作限流。
- **LoggingMiddleware**：每次请求输出 `方法 路径 -> 状态码 (耗时ms)`。

`core/exceptions.py` + `main.py`

- 自定义 `SupportError` 携带 `code / message / status_code / detail`。
- 全局 `exception_handler` 兜底所有未捕获异常，避免堆栈泄漏给客户端。

## 2. 数据库错误安全（SQLite）

`dialog/storage.py`

- **自动提交上下文**：所有写操作通过 `with _db() as db:` 事务提交，异常时自动回滚。
- **幂等写入**：消息对 `user + assistant` 一并落库，保证会话历史一致。
- **路径解析**：`DATABASE_URL` 相对路径自动解析为项目根绝对路径，避免目录不存在导致启动失败。

## 3. LLM 幻觉防护（RAG 确定性兜底）

这是智服通最有工程价值的设计 —— **不把「没有正确答案」交给 LLM 自由发挥**。

```
请求 → 意图识别
        ├─ 问候      → 固定欢迎语
        ├─ 转人工词  → 立即生成工单（不调用LLM）
        └─ 检索+生成
             ├─ 完全未命中(hits为空)  → 兜底话术（不回答）
             ├─ 置信度 < 阈值          → 自动转人工
             └─ 命中且置信度足够        → 流式回答 + 附溯源
```

| 防护点 | 触发 | 行为 |
|---|---|---|
| 检索未命中 | 向量+BM25 混合分 0 | 返回兜底话术，绝不生成虚假答案 |
| 连续低置信 | ≥3 次 | 自动转人工并开单 |
| 敏感词/负面情绪 | 关键词识别 | 立即转人工 |
| 明确要求转人工 | 关键词 | 立即转人工 |

`rag/chain.py` 内对模型输出做 `_strip_confidence_json` / `_parse_confidence`
解析，模型被要求在回答尾部输出 JSON 置信度，前端展示「可信度 xx%」。
